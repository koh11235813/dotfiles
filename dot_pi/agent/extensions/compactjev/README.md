# compactjev

Pi の圧縮 (compaction) の前に、長いツール出力を Jev の採点で絞る拡張。
Pi の要約器はツール結果ごとに頭の 2000 字しか見ないので、頭に並んだ進捗表示が末尾のエラーを要約から押し出す。
compactjev は行ごとに「この出力を理解するのに要るか」を Jev に訊き、順位の高い行を元の順のまま 2000 字に収めて、Pi の要約器に渡す。
要約そのものは Pi が作る。これが既定の lines モード。

もう 1 つ、セッションごとに選ぶ calls モードがある。ツール呼び出しを単位に採点し、LLM の要約を作らずに会話の原文を並べて返す (下の「calls モード」)。
どちらのモードでも、圧縮で文脈から消えた履歴を引き直す道具 `session_recall` をモデルに渡す (下の「session_recall」)。

## 使い方

Jev を使える provider の認証があれば、`/compact` と自動の圧縮のたびに動く。認証が無ければ圧縮には何もしない (`session_recall` は使える)。
採点の目的には `/goal` の文と `/compact` の指示を渡す。どちらも無ければ直近のユーザー発言を使う。

| 操作 | 効果 |
| --- | --- |
| `/compactjev` | 今のモードを表示する |
| `/compactjev calls` | このセッション (の今の枝) を calls モードにする |
| `/compactjev lines` | lines モードに戻す |

選んだモードは custom entry `compactjev-mode` に残り、resume と reload をまたぐ。新しいセッションは lines から始まる。

lines モードでは圧縮のたびに通知が 1 つ出る。全体と出力ごとの字数の減り、落とした行数、失敗した Jev 要求の数、絞らなかった出力の数が載る。

## 絞らないもの

Pi の切り方のほうがましな場合は手を出さない。

| 対象 | 理由 |
| --- | --- |
| 2000 字以下のツール出力 | もともと全部が要約器に届く |
| `!` で実行したコマンドの出力 | Pi は切らずに要約器へ渡す |
| `read`・`grep`・`find`・`ls` の結果 | 中身はファイルの内容やパスの一覧で、飛び飛びの行より頭から続いた 2000 字のほうが読める |
| 空行を除いて 1 行しかない出力 | 順位を付ける相手が無い。Jev にも訊かない (下の「決めたこと」) |
| Jev の要求が 1 つでも失敗した出力 | 採点の無い行が採点済みの行より上に来て予算を食うので、その出力は丸ごと Pi に任せる |
| 1 回の圧縮で採点が 3000 行を超える分 | 費用の上限 |

表の下の 3 行 (1 行だけの出力、Jev の失敗、3000 行超え) は、失敗したツール結果には当てはめない (次の節)。

## 失敗したコマンドの末尾

Pi が失敗と記録したツール結果 (`isError`。bash の 0 でない終了・中断・時間切れと、例外を投げたツール) は、末尾を Jev の採点に関わらず残す。

- 末尾から 600 字に収まる行 (空行は数えない) を、Jev に訊かずに残す。残りの行を Jev が採点し、2000 字の残りに順位の高い順で入れる。
- 最後の行だけで 600 字を超えるなら、その行の終わり側を残す。空行を除いてその 1 行しか無い出力は、頭の 1200 字も残す (採点で選ぶ行が無く、その分の予算が余るため)。
- 採点する行が 1 行以下でも対象から外さない。長い 1 行と終了状態の行だけの出力は、長い行の頭を切り詰め、終了状態の行を残す。
- Jev の要求が失敗した出力、費用の上限で採点しなかった出力、Jev が全滅した圧縮でも、失敗した出力だけは絞る。このときは採点を使わず、元の順のまま頭と末尾を残す。
- calls モードで畳むときは、結果の頭 300 字の代わりに末尾 600 字を残す。

## calls モード

`/compactjev calls` を選んだセッションでは、圧縮のたびに次を行い、Pi の要約の代わりにその結果を返す。

1. 圧縮される範囲 (分割されたターンの前半も含む) を、ユーザーの発言、アシスタントの発言、ツール呼び出し (引数と結果) の並びにする。thinking と画像は持たない。
2. 引数と結果を合わせて 800 字を超え、畳めば短くなる呼び出しだけを Jev に訊く。畳んでも印の分で短くならないもの (引数が 500 字以下で、結果が頭 300 字か失敗の末尾 600 字とほぼ同じ長さ) は訊かずに残し、畳んだ数にも数えない。1 回の要求に 20 件。Jev が見るのは目的と、その 20 件の引数の頭 500 字、結果の頭と末尾 300 字ずつ、結果の字数、失敗したかどうか。
3. 採点が 0.5 以上の呼び出しを、採点の高い順に、予算に収まるかぎり原文のまま残す。予算は Pi の設定 `reserveTokens` の 4 倍の字数 (既定で約 65000 字)。
4. 残らなかった呼び出しは、引数を頭 500 字、結果を頭 300 字 (失敗なら末尾 600 字) に畳み、落とした字数と `session_recall(id="...")` を書いた印を付ける。呼び出しの行そのものは消さない。
5. 発言は 1 字も変えずに元の順で並べる。ユーザーの依頼文が要約器を通ることは無い。

結果は圧縮の entry の `summary` に入り、先頭に「これは要約ではなく会話の原文」という 1 段落が付く。同じ並びを `details.compactjev.items` にも持つ (各呼び出しに `id`・`call`・`result`・`error`・`chars`・`kept`・`probability`)。
次の圧縮では、前回の `details` から並びを組み直し、前回残した呼び出しも新しい範囲と一緒に採点し直す。畳んだ呼び出しは畳んだまま持ち越す。前回の圧縮が Pi の要約だったとき (と、`details` が読めないとき) は、その本文を `[Earlier summary]` として先頭に置く。
`details.readFiles` と `details.modifiedFiles` は Pi の要約と同じ欄で、前回の自分の結果と今回の範囲を合わせる。Pi は拡張が作った圧縮の `details` からファイル一覧を引き継がない (`compaction.js` の `extractFileOperations`) ので、こちらで足し込んでいる。

次のときは結果を返さず、理由を通知して lines モードに落とす (行を絞って Pi が要約する)。

| とき | 通知 |
| --- | --- |
| Jev の要求が 1 つでも失敗した (例外を投げた場合も)、または答えが欠けた | 毎回 warning |
| 採点する呼び出しが 300 を超えた | info |
| 発言と畳んだ呼び出しだけで予算を超えた | info |

3 つ目が、原文の並びが膨らみ続けるのを止める弁になる。発言と呼び出しの行は消さないので、圧縮を重ねると並びは伸びる。予算を超えた回は Pi が前回の並びごと要約し直し、次の calls はその要約を先頭に置いて始まる。

この弁は呼び出しの数で閉じる。畳んだ呼び出しにも、呼び出しの行、結果の頭 300 字、印、前後の発言が残り、1 件あたり 600 字前後になる。`reserveTokens` が既定の 16384 (予算 65536 字) なら、全部を畳んでも 100 件前後で埋まる (偽の Jev が全件に 0 を付ける合成の範囲で測った: 短い発言 1 つ + bash 1 件の組が 100 組で 57825 字、150 組は 86625 字で辞退)。それより呼び出しの多い範囲は、採点と関係なく lines に落ちる。収まった回が予算の近くまで使っていれば、次の圧縮は新しい範囲の分で超えて lines に落ちる。前回の並びを採点し直す道に届くのは、呼び出しの少ないセッションに限られる。実セッションでの呼び出し数の分布は測っていない。

## session_recall

モデルが呼ぶ道具。今の枝のセッション履歴を読むだけで、何も書かない。圧縮は entry を消さないので、圧縮前の発言もツール結果も原文で引ける。

| 引数 | 返すもの |
| --- | --- |
| `query` | 空白で区切った語をすべて含む entry (大文字小文字は区別しない) を新しい順に 10 件まで。`session_recall` 自身の呼び出しと結果は探す対象に入れない (実行中の呼び出しが引数に同じ語を持つので、入れると必ず自分に一致する)。それぞれ entry の id、ツール結果なら toolCallId、種類、字数、最初の語の前後 150 字 |
| `id` | entry の id なら、その entry の本文。toolCallId (calls モードの印に書いてある id) なら、その呼び出しの引数と結果を `[Tool call]: …` `[Tool result]: …` の 2 段で続けて返す (`write` や `edit` は書いた中身が引数にあるので、結果だけでは戻らない)。10000 字ずつで、続きは `offset` |

Pi が文脈から外した entry (`context_edit` の `replacement: null`。Pi 自身も、やり直した応答とそのツール結果をこれで外す) は、検索にも `id` にも出さない。置き換えられた entry は置き換え後の本文で返す。同じ entry への編集が複数あれば後のものを使う。

`readOnlyHint` を付けて登録しているので、guard の `ask` と `readonly` でも確認なしで通る (`guard/permissions.ts` の `judgePermission`)。

## 失敗の知らせ方

- Jev の要求が全部失敗した圧縮は、そのたびに警告を出して何も絞らない。
- 全部失敗しても、失敗したツール結果があればそれだけは絞る (上の「失敗したコマンドの末尾」)。警告の文面がそう変わる。
- 一部だけ失敗した圧縮は、通知の末尾に失敗数を載せる。失敗のあった圧縮 (全滅も数える) が 2 回続き、その回が一部失敗なら、警告を 1 度だけ出す。失敗の無い圧縮を挟むまで繰り返さない。
- 連続の数はセッションをまたがない。new / resume / reload で 0 に戻る。Jev に 1 度も訊かなかった圧縮は、連続の数を変えない。
- calls モードが結果を返せなかったときは、そのたびに理由を通知する (上の表)。連続の数には入れない。

## 損失の記録

lines モードで絞った圧縮のたびに、custom entry `compactjev` をセッションに 1 つ足す。モデルには見えない。
calls モードが結果を返した圧縮では足さない。そのときの記録は圧縮の entry の `details.compactjev.items` で、採点と、畳んだかどうかが呼び出しごとに載っている。
書き込みに失敗したら警告を出し、絞った結果はそのまま Pi に渡す。

| 欄 | 中身 |
| --- | --- |
| `lineChars`・`batchLines` | そのときの設定。1 行のうち Jev に見せた字数 (300) と、1 回の要求に入れた行数 (40) |
| `outputs[]` | 絞った出力。`toolCallId`、`command`、`before` (元の字数)、`after` (絞った後の本文)、`blankLines` (消した空行の数)、`batches` (Jev 要求の数)、`failed` (うち失敗した数。0 でないのは失敗した出力だけで、採点を使わず頭と末尾を残している)、`lines[]` |
| `outputs[].lines[]` | 空行を除いた各行を元の順に。`chars` (元の長さ)、`probability` (Jev の採点。訊いていない行は 1)、`kept`。落とした行だけ `text` (Jev に見せた 300 字まで) を持つ。Jev に訊かずに残した末尾の行は `pinned: true` |
| `unfiltered[]` | 採点が欠けたか費用の上限で絞らなかった出力。`toolCallId`、`command`、`chars`、`batches`、`failed`。本文は持たない |

元の全文は記録に写さない。同じセッションファイルの、`toolCallId` が一致するツール結果にある。

セッションファイル (JSONL) から見る例:

```sh
# 落とした行を、採点の高い順に
jq -r 'select(.type == "custom" and .customType == "compactjev") | .data.outputs[] | .command as $c | .lines[] | select(.kept | not) | [.probability, $c, .text] | @tsv' SESSION.jsonl | sort -rn | head -50

# 300 字を超えていて落とした行 (Jev は頭の 300 字しか見ていない)
jq -c 'select(.customType == "compactjev") | .data as $d | $d.outputs[].lines[] | select((.kept | not) and .chars > $d.lineChars)' SESSION.jsonl
```

40 行ごとの区切りは `lines[]` の位置を `batchLines` で割れば分かる。区切りをまたいで採点の水準がずれているかは、そこから見る。

## 決めたこと

- **記録の置き場はセッションの custom entry。** 別ファイル (`~/.pi/agent/` の下の JSONL) も考えたが、掃除の仕組みが要り、どのセッションの記録かを別に持つことになるので捨てた。
- **記録するのは落とした行の本文だけ。** 元の全文を写すとセッションファイルに同じものが 2 つ入る。1 回の圧縮で最大 3000 行 × 300 字ほど増える。
- **1 行だけの出力は対象から外した。** 以前は切り詰めた印の分だけ予算を空け、約 1760 字しか残らなかった。Pi に任せれば頭の 2000 字が残る。予算を 2000 字いっぱいまで広げる案は、印の長さが畳んだ後でないと決まらず、溢れると行ごと落とす処理に掛かるので捨てた。
- **失敗の判定は `isError` で、終了状態の行の文面は見ない。** 以前は Pi の bash が末尾に足す `Command exited with code N` などの 4 つの形を正規表現で見分け、長い 1 行の失敗を Pi に任せていた。Pi が文面を変えると黙って効かなくなるうえ、任せた先では終了状態の行が落ちる。`isError` は Pi が結果に付ける欄で、bash 以外のツールの失敗にも効く。
- **残す末尾は 600 字。** 2000 字のうち採点で選ぶ分を 1200 字残す配分。スタックトレースの終わり 10 行前後が入る。fast-jev-compaction-pi の `preserveErrorTails` は字数を設定にしているが、設定は足していない。実セッションで測った数字ではない。
- **calls モードは既定にしない。** LLM の要約をやめると、要約が持っていた「何を決めたか」の整理が無くなり、圧縮後の文脈は Pi の要約より大きくなる。issue もこの方式を「採るかどうかは未決」としている。既定を変えるのはユーザーが決めることなので、選んだセッションだけで動く形にした。切り替えを環境変数にする案は、セッションの途中で試して戻すことができないので捨てた。
- **calls モードの採点は Pi の classifier 経由。** fast-jev-compaction-pi は TypeSafe の API を直接叩き、会話全体を state として Jev に渡す。ここでは lines モードと同じ `ctx.modelRegistry.classify` を使い、渡すのは目的とその要求の 20 件だけにした。Jev は発言も、ほかの要求の呼び出しも見ない。「後の呼び出しで置き換えられた」の判断は同じ 20 件の中でしか効かない。
- **calls モードは 1 つの呼び出しに質問 1 つ。** fast-jev-compaction-pi は「呼び出しを残すか」「結果を残すか」の 2 つを訊き、呼び出しごと消す道がある。ここでは呼び出しの行を常に残す。同パッケージが「正確なコマンドを 8/8 残した」と計測したのは、消した呼び出しにも 1 行の記録を残す設定のほうなので、それを固定にした。
- **calls モードの残す・畳むは閾値 0.5 と予算の両方。** lines モードが閾値を使わないのは、行の採点では要る行と要らない行の絶対値が重なるから。呼び出し単位で順位と予算だけにすると、要らない呼び出しでも予算いっぱいまで原文が残る。0.5 は fast-jev-compaction-pi の既定で、ここで較正した値ではない。採点は `details` に残るので後から見直せる。
- **calls モードの予算は `reserveTokens` の 4 倍の字数。** Pi 自身の要約がこの枠の中に収まるので、同じ枠を借りた。fast-jev-compaction-pi の「範囲の 25% 以上減れば採用」は、圧縮後の大きさに上限が付かないので捨てた。
- **`details` には要約と同じ本文がもう 1 度入る。** lines モードの記録では写しを避けたが、次の圧縮で採点し直すには、残した呼び出しの原文が構造のまま要る。`summary` の文字列から組み直す案は、ツール結果の中に同じ見出しが出ると壊れるので捨てた。
- **toolCallId で引くと、引数と結果をまとめて返す。** 引数だけを返す引数 (`part`) を足す案は、畳んだ印とツールの説明の両方で使い分けを教えることになるので捨てた。長い引数の後ろにある結果は `offset` で進んで読む。
- **session_recall が探すのは今の枝の全部。** 圧縮前だけに絞る案は、境目の計算が要るわりに、モデルが訊くのは手元に無いものだけなので得が小さい。探し方は語の部分一致で、点数づけはしない。
- **連続失敗の警告は 2 回目。** 1 回きりの失敗は通知の末尾で足りる。

## できないこと

- **ツール結果ごとの 2000 字を超えて残すこと。** 切っているのは Pi 本体 (`compaction/utils.js` の `TOOL_RESULT_MAX_CHARS`) で、設定は無い。Pi が公開している `compact` と `generateSummaryWithUsage` は、どちらも同じ切り方を通る。超えるには要約を拡張で作って返すことになる。API としてはできる: 公式 sample の `examples/extensions/custom-compaction.ts` は、自前のプロンプトと `ctx.modelRegistry.complete` で要約を作り、`session_before_compact` から `compaction` として返している。作っていないのは API の制約ではなく判断による。Pi 自身の要約用プロンプト 3 つと `completeSummarization` は公開されていないので、同じ質の要約を出すにはプロンプトを写すか書き直すことになり、写せば Pi の更新で黙ってずれ、書き直せば要約の形が Pi のものと変わる。どちらを取るかはユーザーが決めること。1 つの結果を 2000 字以下の複数のメッセージに割って渡す手もあるが、Pi の直列化の内部に頼るうえ、要約器に送る量をどこまで増やすかの判断が要るので入れていない。
- **1 行 300 字・40 行ごとの採点・空行の削除が、実際にどれだけ損をしているかの判定。** 上の記録で測れるようにしただけで、実セッションの数字はまだ無い。数字が出るまで挙動は変えていない。
- **lines モードで、ユーザーの依頼文を要約の後ろに原文のまま足すこと。** lines モードは何も返さず Pi に要約させるので、要約の文字列に触れる場所が無い (`session_compact` は書き込み済みの entry を知らせるだけ)。足すには Pi が公開している `compact()` を拡張から呼んで結果を返すことになるが、Pi が内部で渡している再試行の設定、仮想モデルの解決、認証つきの stream 関数は拡張から取れず、実物の provider で確かめる手段もここには無い。上の「2000 字を超えて残すこと」と同じく、要約を拡張で作るかどうかの判断になる。依頼文が原文で残るのは calls モードだけ。
- **calls モードで、発言を減らすこと。** ユーザーとアシスタントの発言、`!` で実行したコマンドの出力、呼び出しの行は畳まない。これだけで予算を超えたら Pi の要約に落ちる。そのとき依頼文は要約器を通る。
- **calls モードで、ほかの拡張の custom message を畳むこと。** guard の monitor が送る job の知らせ (`monitor-event`。出力の末尾を 80 行・8 KiB まで載せる) と、verify が失敗を差し戻す文 (`verify`。同じく 8 KiB まで) は、Pi が custom message を user の発言に直してから渡すので (`convertToLlm`。Pi 自身の要約器も同じ扱い)、`[User]:` として全文が残る。本文の「This is not a message from the user.」という断りはそのまま残る。monitor と verify を使うセッションでは、これが畳めない量の主な部分になる: 8 KiB の知らせが 9 つあるだけで、発言だけで 73874 字になり、既定の予算 65536 字を超えて lines に落ちた (レビューでの実測。理由は通知される)。畳むには、発言と別の種類として並びに持ち、`session_recall` で引き直せる形にする必要があり、圧縮の `details` の形が変わる。入れていない。
- **calls モードの予算を、実際のトークン数で掛けること。** 予算は字数 (`reserveTokens` の 4 倍) で、1 トークン 4 字という見積もりは Pi 自身のもの (`compaction.js` の `estimateTokens`) と同じ。ただし Pi の要約は API の `maxTokens` (`reserveTokens` の 0.8 倍) で実際のトークン数に収まるのに対し、こちらは字数でしか縛れない。日本語は 1 字が 1 トークン前後なので、日本語の発言が多いセッションでは、返す本文がトークン数で枠の数倍になりうる (発言 6 万字なら約 6 万トークン)。予算超えで Pi の要約に落とす弁も、その分だけ遅く閉じる。provider の tokenizer は拡張から使えず、ASCII 以外の字を重く数える見積もりは測った根拠が無いので入れていない。
- **calls モードの閾値・予算・質問文の較正。** Jev の実物で試していない。テストは偽の Jev が返す採点に対する動きだけを見ている。
- **calls モードから lines モードへ戻したあとのファイル一覧の引き継ぎ。** Pi は拡張が作った圧縮の `details` を読まないので、calls の間に触ったファイルは Pi の要約の `<read-files>` に載らない。呼び出しの行としては前回の本文に残っている。
- **Jev の認証が無いとき、中断したときに、失敗したコマンドの末尾を残すこと。** 拡張ごと何もしない。
- **`read`・`grep`・`find`・`ls` の失敗と、`!` で実行したコマンドの失敗。** 対象外のまま。
- **calls モードの中で Jev が例外を投げたときに、行の絞り込みまで続けること。** calls は理由を通知して lines に落ちるが、lines の採点で同じ例外が出れば、その圧縮は何も絞らない。
- **session_recall で、今の枝に無い履歴を引くこと。** `/tree` で離れた枝や別のセッションは読まない。thinking と画像も返さない。
- **複数行の出力で、長い 1 行を切ったときの余り。** 切り詰めの印と畳んだ印の分、2000 字より 100 字前後短くなる。
- **古い記録の掃除。** セッションファイルに残り続ける。
- Jev が全滅して失敗したツール結果も無かった圧縮、中断した圧縮、対象が無かった圧縮では記録を残さない。
- **記録が表すのは「Pi の要約器に何を渡したか」まで。** 書くのは要約の前なので、そのあと Pi の要約が失敗しても記録は残る。要約に何が残ったかも分からない。
