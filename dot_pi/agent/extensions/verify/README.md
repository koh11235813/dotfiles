# verify

完了前の自動検証。
人が project ごとに登録した検証コマンドを、ファイルを変えたタスクの終端で走らせ、失敗したらモデルへ差し戻す。
Pi 1.1.0 の `agent_before_settle` と `agent_settled` を使う (`dist/core/extensions/types.d.ts` に実在する)。

## 使い方

| 入口 | 内容 |
| --- | --- |
| `/verify` | 今の結果と、この project に登録したコマンドの一覧 |
| `/verify add <command>` | コマンドを末尾に登録する。`add` より後ろの全文が 1 つのコマンドで、`/bin/bash -c` に渡す |
| `/verify remove <number>` | 一覧の番号で外す |
| `/verify stop` | 走っている検証を止める |

この dotfiles なら `/verify add node dot_pi/agent/tests/run.mjs`。
モデルから呼べるツールは無い。登録できるのは人だけで、`/verify add` と打つことが承認にあたる。

登録は `~/.pi/agent/verify.json` (`PI_CODING_AGENT_DIR` があればその下) に置く。
project の中 (`.pi/` など) には置かない。そこはモデルが edit / write で書き換えられるので、人の承認を経ていないコマンドが走ってしまう。
鍵は worktree が共有する git ディレクトリ (`git rev-parse --git-common-dir`) で、同じリポジトリなら下の階層や別の worktree から起動しても同じ登録を使う。
コマンドは、いま居る作業ツリーの最上位で走る。

`verify.json` が在るのに読めない (壊れた JSON、知らない形) ときは、`/verify add` と `/verify remove` は警告を出して何も書かない。空として書き直すと、他の project の登録ごと消えるため。その間は登録なしとして扱い、検証は走らない。
書き込みは一時ファイルに書いてから rename するので、途中で落ちても半端な JSON は残らない。

## いつ走るか

タスクは、最初の `agent_start` から `agent_settled` まで。

1. タスクの最初に作業ツリーの状態を取る。
2. `agent_before_settle` で状態を取り直す。タスクの最初と同じなら走らせない。
3. 違えば、登録順に 1 つずつ走らせる。最初に失敗したところで止める。
4. 失敗したら、コマンド・終わり方・出力の末尾 (80 行・8 KiB まで) を `verify` という custom message にして `continue: true` を返す。モデルがもう 1 度動き、2 に戻る。
5. `agent_settled` で最終結果を `ctx.ui.notify` で 1 度だけ知らせる。途中の失敗では知らせない。結果が前と変わらなかったタスク (変更なし) でも知らせない。

`agent_before_settle` の時点で、他の拡張が続行を決めているか、入力 (steer / follow-up) が待っているときは走らせない。モデルがまだ動くので、確かめるのは次の境界に回す。
他の拡張の続行を Pi が退けて次の境界が来なかったときは、`agent_settled` で未実行にする。
エラーで終わったタスク (`outcome` が `error`) も確かめるが、モデルへは戻さない。

## 結果の 4 つの状態

フッターの status (`verify`) と `/verify` に、いつも次のどれかを出す。登録の無い project では何も出さない。

| 表示 | 意味 |
| --- | --- |
| `検証: 未実行 (理由)` | 今の作業ツリーは確かめていない。理由は下の表 |
| `検証: 成功` | 登録した全コマンドが 0 で終わった。確かめたのはそれだけで、作業の成否ではない |
| `検証: 失敗 (コマンド: 終わり方)` | 0 以外で終わった、シグナルで死んだ、起動できなかった、timeout を過ぎた |
| `検証: 中断 (コマンド の途中で止めた)` | 走っている検証を Esc・`/verify stop`・セッションの終わりで止めた |

走っている間は `検証: 実行中 (1/2 コマンド)`。

未実行の理由:

| 理由 | いつ |
| --- | --- |
| このセッションではまだ確かめていない | セッションの最初。結果はメモリの中だけにあり、quit / resume / reload をまたがない |
| 確かめた後にファイルが変わった | 成功か失敗が出た後で、作業ツリーの状態が変わった |
| 確かめた後に登録が変わった | 成功か失敗が出た後で、`/verify add` / `remove` で登録が変わった (別のセッションからでも)。走らせていないコマンドがあるのに成功、外したコマンドの失敗、を残さない |
| 検証中にファイルが変わった | 走らせる前と後で状態が違う。成功でも失敗でも結果を使わず、モデルへも戻さない |
| タスクが中断されたので確かめていない | Esc で止めたタスクがファイルを変えていた。Pi は中断したタスクに `agent_before_settle` を送らない |
| 確かめないままタスクが終わった | ファイルを変えたタスクが、検証を後に回したまま終わった |
| git からファイル状態を取れなかった | `git ls-files` が失敗した |

## ファイル状態

git が無視していないファイル (追跡済みと未追跡) のパス・種類・実行ビット・中身の SHA-256 (symlink はリンク先の文字列)。
作業ツリーの中に別の git リポジトリ (submodule も) があれば、その中でも同じ値を取って混ぜる。git は外側の一覧にその中身を出さないため。
成功と失敗は、この値と、そのとき走らせた登録 (コマンドの並び) に結び付く。`git add` や commit では変わらないので、成功の後に commit しても成功のまま。

確かめ直すのは、タスクの最初、`agent_before_settle`、`agent_settled`、`/verify` を打ったとき。ファイル状態か登録が変わっていれば未実行に戻す。
同じ状態を同じ登録で 2 度は確かめない。差し戻してもモデルが何も変えなければ、走らせ直さずにそこで終える。

捨てた案:

- edit / write の成功だけを数える: bash 経由 (sed、formatter、mv)、人、別 agent、monitor の job の変更を見落とす。
- 一時 index に `git add -A` して tree の hash を取る: 利用者の `.git/objects` に書き込む。
- mtime とサイズ: 速いが、中身が変わっても同じ値になる書き方 (`cp -p` など) がある。

## 上限

| 何 | 値 | 理由 |
| --- | --- | --- |
| 差し戻し | 1 つのタスクで 2 回 (検証は最大 3 回走る) | 1 回では直し損ねを拾えず、多いと同じ失敗で回り続ける。上限に達したら失敗のまま終え、理由に書く |
| timeout | コマンド 1 つあたり 5 分 | この dotfiles のテストは数秒。過ぎたら失敗として差し戻す |
| 止め方 | プロセスグループに SIGTERM、2 秒後に SIGKILL | monitor と同じ |

どれも設定にはしていない (`index.ts` の `limits`)。

## できないこと

- **guard の sandbox とモード判定を通らない。** 検証コマンドは拡張のプロセスから直接起こすので、`/permissions` が readonly でも、Pi と同じ権限で走り、書き込める。guard が包むのは自分のツール (bash、monitor) だけで、他の拡張から sandbox を借りる口が無い。
- **承認しているのはコマンドの文字列で、それが実行する中身ではない。** 登録したコマンドが読むテストコード・`package.json` の scripts・Makefile などは root の中にあり、モデルが edit / write で確認なしに書き換えられる。その中身が、タスクの終端で、確認なしに、guard の sandbox の外で走る。normal の bash からは読めない・書けない場所 (`~/.ssh`、`~/.zshrc`、`verify.json` 自身など) にも届く。verify の中からは塞げない (上の項目と同じ理由)。信用できないタスクでは登録を外しておく。
- **`verify.json` を書けるモードでは、モデルが登録を書き換えられる。** full では止めるものが無い。normal 以下では guard が `~/.pi` を書ける場所に足していない (`guard/sandbox.ts` の `EXTRA_WRITE_PATHS`) が、`~/.pi` を含む場所で Pi を起動すれば書ける。
- **git リポジトリの外では使えない。** ファイル状態を git の一覧から作るため。`/verify add` は断る。
- **複数の Pi が同時に `/verify add` / `remove` すると、後から書いた方が残る。** 読んでから書くまでの間に鍵を掛けていない。
- **git が無視しているファイルの変更は見えない。** ビルド成果物だけが変わっても、変更なしとして扱う。初期化していない submodule (`.git` の無い空のディレクトリ) の中も見ない。
- **追跡下のファイルを書き換える検証コマンドは、毎回「検証中にファイルが変わった」になる。** formatter の `--write` や、無視していない場所に成果物を吐くテストなど。誰が変えたかは区別できない。
- **走っている間に変わって元に戻った場合**は気付かない。見ているのは走らせる前と後だけ。
- **Esc で止まるのは TUI だけで、鍵は Escape に固定。** 境界の間は `ctx.signal` が無いので、端末の生の入力から Escape を拾っている。`app.interrupt` を別の鍵に割り当てていると、その鍵ではタスクは中断されるが検証は止まらず、終わるか timeout まで待つ。`/verify stop` はどのモードでも効く。検証中に別の用で Escape を押しても (補完を閉じるなど) 検証は止まる。
- **status の表示は最後に確かめ直した時点のもの。** タスクの外で人や job がファイルを変えても、次のタスクの最初か `/verify` までは `成功` のまま出ている。
- **print / json モード (`pi -p`、subagent の子) でも走る。** 子が変更を加えるたびに子の中で検証が走り、親でももう 1 度走る。並列の子は互いの書きかけを見るので、「検証中にファイルが変わった」になりやすい。子を見分ける口が無いので止めていない。
- **状態を取る時間はファイル数と大きさに比例する。** 1 つのタスクで 2〜3 回、無視されていない全ファイルを読む。
- **`setsid` でグループを抜けた子孫は止められない。** シェルが終わってから 250 ms だけ出力を待ち、残っていても先へ進む。
- **agmsg の完了報告には載せない。** このホストに agmsg が無い。
- **人が手で走らせ直す入口は無い。** 中断や未実行の後 (登録を変えた後も) は、`!` でコマンドを打つか、次にファイルを変えるタスクを待つ。
- 型検査はしていない (このリポジトリに tsc が無い)。API は型定義を読んで合わせた。実物の TUI での見え方 (status、custom message、Esc) も確かめていない。
