# guard / monitor

bash を待たずに走らせるバックグラウンド job。
guard の一部で、`guard/index.ts` が読み込む。Pi が自動検出するのは `extensions/*/index.ts` の 1 段だけなので、このディレクトリは単独の拡張としては読み込まれない。

## 使い方

| 入口 | 相手 | 内容 |
| --- | --- | --- |
| `monitor({ command, timeout? })` | モデル | job を起動し、id とログのパスをすぐ返す。`timeout` は秒で、既定は無し |
| `jobs({ action, id? })` | モデル | `list` / `log` / `stop`。`log` と `stop` は id が要る |
| `/jobs`、`/jobs log <id>`、`/jobs stop <id>` | 人 | 同じ操作 |
| `/monitor` | 人 | 実行状態の表示。走っている数と終わった数、job ごとに状態・経過時間・コマンドの全文・ログのパス |

job が終わると、`monitor-event` という custom message を 1 度だけ送る (下の「知らせ」)。
`jobs stop`・`/jobs stop`・モードの変更で止めた job はターンを起こさず、次のターンに添える。

## 知らせ

知らせの入口は 1 つで、job の終了も、ほかの拡張からの知らせも同じ決まりで届く。

- 載せるのは、1 行の要約 (200 字まで)、完全なログの場所、出力の末尾 (80 行・8 KiB まで) だけ。生の出力は流さない。通知元が長い出力を渡しても、ここで切る。
- 送るのは Pi が idle になってからで、そこで新しいターンを起こす。ターンや圧縮の途中に来た知らせは、それが済むまで待つ。ターンの途中で後続 (follow-up) として積まないのは、Esc の中断がキューごと捨てるため。
- 人の入力を受けてからターンが始まるまでの間も待つ。Pi はその間 idle に見えるので、待たないと知らせのターンが先に始まり、入力が「処理中」で断られる。待つのは `input` から `agent_start` までで、ターンが始まらなかった入力 (ほかの拡張が処理した、モデルや認証が無くて失敗した) は 5 秒で見切る。

### 種類

知らせは種類を 1 つ持ち、本文の 1 行目 (`[種類] 通知元: 要約`) と `details.kind` に出る。種類ごとに、それが何を意味しないかを本文に書く。

| 種類 | 意味 | 意味しないこと |
| --- | --- | --- |
| `received` | 何かが届いた | 読んだ・処理した・返事した |
| `process-ended` | プロセスが終わった | 終了コード 0 でも、検証の合格ではない |
| `verified` | 検証コマンドが、走った時点のファイルに対して通った | その後の変更は含まない |
| `request-done` | 相手が依頼を終えたと言っている | こちらでは結果を確かめていない |

この拡張が自分で出すのは `process-ended` (bash の job) だけ。bash は終了の知らせだけを出し、途中の出力は知らせない。
ほかの 3 つは、下の入口に流す拡張がいて初めて届く。いまは流す拡張が無い (agmsg の受信、検証の結果、依頼の完了はどれも未接続)。

### ほかの拡張からの入口

`pi.events.emit("monitor:event", event)` で流す。`event` は次の形。

| 項目 | 中身 |
| --- | --- |
| `kind` | 上の 4 つのどれか |
| `source` | 通知元の名前 (`inbox` など)。見出しに載せるのは 1 行目だけ |
| `id` | 通知元の中で一意な id |
| `summary` | 1 行の要約 |
| `tail` | 出力の末尾 (省ける)。stream の通知元は、出力のまとまりごとに 1 つの知らせを流す |
| `logPath` | 完全なログの場所 (省ける) |
| `wake` | `false` なら、ターンを起こさず次のターンに添える (省ける) |

形の合わないものは届けず、warning を出す。
同じ `kind`・`source`・`id` の知らせは 1 度しか届けない (直近 256 件を覚える)。通知元が同じ未読を繰り返し流しても、ターンは 1 度しか起きない。
guard の `session_start` より前に流された知らせは捨てず、`session_start` の後で届ける。

### 自分自身を起こし続けないために

知らせで始まったターンが job を起こし、その job の終了がまたターンを起こす、という連鎖は人なしで回り続ける。これを 3 回で止める。

- 知らせは、それが生まれたターンの「段」を持つ。人の入力で始まったターンは 0 段目、知らせで始まったターンは、その知らせの段 + 1。
- 3 段目のターンで生まれた知らせはターンを起こさず、次の人の入力に添える。そのとき warning を出す。
- 人の入力 (`input` の `source` が `extension` でないもの) で 0 段目に戻る。入力より前に生まれてまだ届いていない知らせ (走っている job の終了、idle を待っている知らせ) も、0 段目のものとして届く。
- 人のターンで並べて起こした job はどれも 0 段目なので、いくつ終わっても起こす。
- ほかの拡張からの知らせは、どのターンが原因か分からないので、届いた時点のターンの段で数える。人がいない間に無関係な知らせが 4 つ続けて届くと、4 つ目は起こさない。
- 3 回という数は、「ビルドが落ちた → 直して走らせ直す → 通った」の 1 往復を人なしで終えられる回数として選んだ。1 回で止める案 (知らせのターンで起こした job は一切起こさない) は、この往復が止まるので捨てた。「人の入力なしに起こした回数」で数える案は、人のターンで並べた job まで止まるので捨てた。

## 権限

`monitor` は bash と同じ扱いを受ける。

- 固定の規則表 (`rules.ts` の `BASH_RULES`) は full を含むどのモードでも効く。
- full 以外では bash と同じ sandbox の中で走る。sandbox が無ければ起動しない。
- ask では起動のたびに確認する。readonly では読み取り専用の sandbox の中で起動できる。

`jobs` と `/jobs` はどのモードでも確認なしで通る。
届くのはこのセッションが起こした job だけで、任意の PID やパスは指定できない。

sandbox は起動したときのモードで決まり、走っている間は変わらない。
そのため `/permissions` でモードを厳しい側 (full → normal → ask → readonly の向き) へ変えると、走っている job を全部止める。
緩める側では止めない。

## job の終わり方

| state | 意味 |
| --- | --- |
| `running` | 走っている |
| `succeeded` | シェルが 0 で終わった。確かめたのはそれだけで、作業の成否ではない |
| `failed` | 0 以外で終わった、こちらが送っていないシグナルで死んだ、ログが上限に達した、ログに書けなかった |
| `stopped` | `jobs stop` か、モードを厳しくしたことで止めた |
| `timed_out` | `timeout` を過ぎた |
| `interrupted` | セッションの終わりか `/tree` で止めた |

止めるときはプロセスグループに SIGTERM を送り、2 秒待って SIGKILL を送る。
シェルが終わった時点でグループに残っている子 (`sleep 100 &` など) も止める。

Linux では、グループを抜けた子孫 (`/proc` で探す) に先に SIGTERM を送り、それが終わるのを 2 秒まで待ってからグループに送る。
sandbox の中身がこれに当たる。bubblewrap は `--new-session` で中身を別のセッションにするので、グループには launcher だけが残り、launcher に SIGTERM を送ると中身は pid namespace ごと即座に消える。先に中身へ送るので、sandbox の中の `trap ... TERM` の後始末が走る。
捨てた案は、job のときだけ `--new-session` を外すこと (sandbox の引数を bash と分けることになる)。

Pi のプロセスが後始末なしに死んだとき (クラッシュ、SIGKILL、端末が消えて `session_shutdown` を待ってもらえなかったとき) は、job のシェルの前に置いた見張りが job を止める。
Pi は job ごとにパイプを 1 本開けたままにしていて、見張りはその EOF を待つ (ポーリングしない)。EOF が来たらグループに SIGTERM、2 秒後に SIGKILL を送る。

## セッションとの関係

- job はそれを起こしたセッションのもの。quit / new / resume / fork / reload で全部止め、止まるのを待ってから次へ進む。
- `/tree` で枝を移ったときも止める。移る前の枝の結果を別の枝に届けないため。
- そこで止めた job と、まだ知らせていなかった job (直前に終わったもの、idle を待っていたもの) の知らせは届かない。次のセッションの一覧は空から始まる。

## 上限

- 同時に走らせられるのは 4 つ。
- 一覧に残す終わった job は 16 個。古いものから忘れる。
- ログは job ごとに 10 MiB。達したら job を止めて `failed` にする。

## ログ

`$TMPDIR/pi-jobs-XXXXXX/<id>.log` (ディレクトリは 0700、ファイルは 0600)。stdout と stderr を届いた順に書く。
セッションが終わっても消さない。あとで読めるようにするためで、片付けは OS の一時ディレクトリの掃除に任せている。

## できないこと

- **print / json モード** (`pi -p`、subagent の子) では `monitor` は起動を断る。最後のターンで閉じるので、知らせを受け取る相手がいない。
- **再起動をまたいだ再接続**はしない。job の一覧はメモリの中だけにある。
- **端末が消えたとき** (SSH の切断など) の動きは、実物の端末では確かめていない。Pi 1.1.0 の対話モードは SIGHUP で `session_shutdown` を呼ぶ (`modes/interactive/interactive-mode.js` の `registerSignalHandlers`) ので、そこで job を止める。呼ばれなかったときと、止め終わる前に Pi が死んだときは、上の見張りが止める。テストで確かめたのは、持ち主のプロセスを SIGKILL したときに job が消えることだけ。
- **見張りが止めるときは、sandbox の中の後始末は走らない。** グループの外の子孫を探して先に送る役が居ないので、launcher に SIGTERM が届いて中身は即座に消える。
- **見張りの分、job のシェルが少し変わる。** コマンドの前に 1 行足すので、シェルのエラーに出る行番号が 1 つずれる。見張りは job のシェルの子にしていない (孫として起こして手放す) ので、引数なしの `wait`、`jobs`、`$!` には出ず、`$$` も変わらない。同じプロセスグループには居るので、コマンドが自分のグループを `ps` や `pkill -g` で数えると 1 つ多く見える。
- **シグナルを送れない job** (`sudo` で root になったものなど) は止められない。止める操作もセッションの終わりも 5 秒 (グループの外の子孫が居なければ 3 秒) で待つのをやめ、job を `running` のまま残して進む。
- **人の入力と重なったときの待ちは、狭めただけ。** 待ち始めるのは Pi が `input` を出してから。それより前 (入力欄で Enter を押してから `input` まで) と、5 秒を過ぎてもターンが始まらないとき (認証の更新が遅い) は、今までどおり知らせのターンが先に始まりうる。
- **`setsid` でグループを抜けた子孫**は、止める操作のときしか止められない (Linux だけ)。そのときまだ job のシェルの子孫であるものを探して止める。シェルが自分で終わった後に残ったものと、親が先に終わって init に引き取られたものは、もう探せないので残る。macOS では止める操作でも残る。Linux の bubblewrap の中では pid namespace ごと消えるので残らない。
- **グループの外の子孫は pid で覚える。** 止め始めたときに 1 度探し、最大 4 秒後に SIGKILL を送る。その間に終わって pid が別のプロセスに使い回されていると、そこへ届く。pid が一巡する間の話で、実害は見込んでいない。
- 配送の失敗のうち、こちらで気付けるのは `sendMessage` がその場で投げたものだけ。そのときは警告を出し、job の結果は `/jobs log <id>` で読める。
- 出力の末尾は通知元が吐いたものをそのまま載せる。指示として扱わないよう知らせの本文に書いているが、強制はできない。
- **種類は通知元の自己申告。** `verified` と名乗る知らせが本当に検証の結果かは確かめない。流せるのは Pi のプロセスの中の拡張だけで、sandbox の中のコマンドからは流せない。
- **連鎖を止めるのは、ターンを起こすことだけ。** 止めた知らせも次の人の入力には添える。モデルが知らせを待たずに `bash` で `sleep` して job を見に行く形の繰り返しは数えない。
